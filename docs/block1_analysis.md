# Блок 1. Анализ и проектирование

## 1.1 Сбор и анализ требований

### Бизнес-задача

Внеплановый отказ двигателя ведёт к простою, срочному ремонту и рискам безопасности. Обслуживание по
регламенту, наоборот, заставляет менять исправные узлы раньше срока. Нужна система, которая по показаниям
датчиков заранее предупреждает об отказе, чтобы ремонт можно было запланировать.

### ML-постановка

- **Тип задачи:** бинарная классификация.
- **Данные:** NASA C-MAPSS, поднабор FD001 (100 двигателей в обучающей части, наблюдения от запуска до отказа).
- **Объект:** состояние двигателя на конкретном цикле (3 режимных параметра и 21 датчик, плюс признаки
  по истории двигателя).
- **Целевая переменная:** 1, если до отказа осталось 30 циклов или меньше, иначе 0. Положительный класс
  составляет около 15% строк.
- **Выход:** вероятность отказа и флаг тревоги по порогу. Порог подбирается под ограничение Recall.
- **Разбиение на выборки:** по двигателям, а не по строкам, чтобы исключить утечку данных.

### Метрики успеха

| Уровень | Метрика | Цель | Обоснование |
|---|---|---|---|
| Бизнес | Доля отказов, о которых предупредили заранее | ≥ 85% | Пропуск отказа — самая дорогая ошибка |
| Бизнес | Доля ложных тревог среди исправных состояний | < 15% | Каждая ложная тревога — лишний осмотр и простой |
| Бизнес | Запас времени от первой тревоги до отказа | медиана ≥ 15 циклов | Нужно успеть заказать запчасти и спланировать ремонт |
| Бизнес | Ожидаемая стоимость ошибок | ниже, чем при обслуживании по регламенту | Расчёт по матрице стоимости ошибок |
| ML | Recall | ≥ 0,85 | Требование задания |
| ML | False Positive Rate | < 0,15 | Требование задания |
| ML | PR-AUC | основная метрика сравнения моделей | Устойчива к дисбалансу классов, не зависит от порога |
| ML | F2-мера | вспомогательная | Взвешивает Recall выше Precision |
| Система | Время инференса | p95 < 50 мс на запрос | Требование задания |

### Функциональные требования

1. Загружать показания датчиков из файлов и из потока сообщений.
2. Хранить данные в PostgreSQL по слоям: raw, cleaned, enriched, features.
3. Рассчитывать признаки по истории двигателя (скользящие средние, отклонения, тренды).
4. Выдавать вероятность отказа в горизонте 30 циклов и флаг тревоги.
5. Предоставлять предсказания через REST API с валидацией входных данных.
6. Сохранять предсказания для последующего мониторинга качества.
7. Обеспечивать воспроизводимое переобучение и версионирование модели.

### Нефункциональные требования

| Категория | Требование |
|---|---|
| Производительность | Инференс p95 < 50 мс; обработка потока не менее 100 сообщений в секунду |
| Режим работы | Предсказание обновляется при поступлении каждого нового цикла |
| Надёжность | Сообщение не теряется: смещение в Kafka фиксируется только после записи в БД |
| Воспроизводимость | Фиксированные версии библиотек и seed, запуск одной командой через Docker Compose |
| Качество кода | Покрытие тестами > 60% |
| Наблюдаемость | Логи запросов, метрики задержки, контроль дрейфа входных данных |

### Допущения и ограничения

- 7 дней из задания приравнены к 30 циклам (около 4 полётов в сутки): в датасете время измеряется в циклах.
- Соотношение стоимости ошибок «пропуск : ложная тревога» = 10 : 1 — экспертная оценка.
- Целевые значения «запас времени ≥ 15 циклов» и «100 сообщений в секунду» заданы автором проекта.
- Данные симуляционные, один режим работы и один тип отказа. Переносимость на реальный парк не проверяется.

## 1.2 Архитектура решения

Диаграмма: `docs/architecture.png` (исходник — `scripts/draw_architecture.py`).

| Компонент из задания | Реализация | Технологии |
|---|---|---|
| Источники данных | Файлы C-MAPSS, симулятор датчиков, web scraping | Python, kafka-python, requests, BeautifulSoup |
| Хранилища данных | PostgreSQL со слоями и журналом предсказаний; Redis | PostgreSQL, Redis |
| Обработка данных | ETL-пайплайн (пакетная загрузка), Kafka с потребителем (поток) | pandas, SQL, Apache Kafka |
| Обучение модели | Обучение с кросс-валидацией по двигателям | scikit-learn, градиентный бустинг |
| Оценка и мониторинг модели | Оценка (Recall, FPR, PR-AUC, порог), контроль качества по журналу предсказаний | scikit-learn |
| API | Сервис `/predict` и `/health` | FastAPI, Pydantic |
| Система мониторинга | Задержка и ошибки API, дрейф данных, сигнал на переобучение | метрики сервиса, SQL-запросы к журналу |

**Пакетный поток (обучение).** Файлы проходят через ETL в слой raw, затем по слоям до features; на них
обучается и оценивается модель, которая сохраняется в файл с метаданными версии.

**Потоковый поток (работа в реальном времени).** Симулятор отправляет показания в Kafka; потребитель пишет
их в raw и фиксирует смещение только после успешной записи. Свежие признаки попадают в Redis, откуда API
берёт их для предсказания.

## 1.3 Планирование экспериментов

### Гипотезы

Общий протокол: разбиение по двигателям, уровень значимости α = 0,05.

| № | Гипотеза | Метрика | Метод проверки | Критерий подтверждения | Результат |
|---|---|---|---|---|---|
| H1 | Признаки по скользящему окну повышают качество по сравнению с исходными показаниями датчиков | PR-AUC | Кросс-валидация на 10 блоков по двигателям, одна модель на двух наборах признаков; односторонний критерий Уилкоксона для парных оценок | p < 0,05 и прирост > 0 | **Подтверждена.** Логистическая регрессия: 0,954 → 0,993; градиентный бустинг: 0,954 → 0,991; прирост во всех 10 блоках, p = 0,001 (`notebooks/03_model_selection.ipynb`) |
| H2 | Градиентный бустинг превосходит базовую логистическую регрессию | PR-AUC | Те же 10 блоков, парное сравнение, критерий Уилкоксона | p < 0,05 и прирост > 0 | **Не подтверждена.** Бустинг 0,9907 против 0,9932 у логистической регрессии, лучше в 2 блоках из 10, p = 0,98 |
| H3 | Финальная модель с подобранным порогом выполняет бизнес-требования на отложенных двигателях | Recall, FPR | Бутстрап по двигателям на тестовой выборке (1000 повторов), 95% доверительные интервалы | Нижняя граница Recall ≥ 0,85 и верхняя граница FPR < 0,15 | **Не подтверждена.** Модель v2 на test: Recall 0,714 (95% ДИ 0,59–0,80), FPR 0,001 (95% ДИ 0,0005–0,0017). По FPR критерий выполнен, по Recall — нет (`notebooks/04_final_model.ipynb`) |
| H4 | Время ответа сервиса укладывается в требование | Задержка, p95 | 1000 последовательных запросов к `/predict` после прогрева | p95 < 50 мс | заполнить после блока 5 |

Десять блоков выбраны потому, что при пяти парных оценках критерий Уилкоксона не может дать p < 0,05.

### План A/B-теста

**Сравниваемые версии.** Вариант A (baseline) — логистическая регрессия, версия v1. Вариант B — финальная
модель, версия v2.

**Источники данных.**
- Поток показаний из топика Kafka `sensor-readings`.
- Таблица `predictions` в PostgreSQL: двигатель, цикл, версия модели, вероятность, флаг тревоги, время ответа.
- Фактические исходы: в эксплуатации — журнал отказов и ремонтов; в проекте — тестовые двигатели FD001
  с известным остаточным ресурсом, которые симулятор воспроизводит как поток.

**Методология.**
1. Этап 1, теневой режим: обе модели оценивают все двигатели, решения принимаются по v1. Сравнение парное,
   критерий Мак-Немара по несовпадающим исходам.
2. Этап 2, разделение трафика: двигатели делятся 50/50 по хешу идентификатора. Единица рандомизации —
   двигатель, так как циклы одного двигателя зависимы.
3. Основная метрика: доля отказов, перед которыми тревога поднята заранее. Сравнение долей — z-критерий,
   при малых выборках — точный критерий Фишера.
4. Ограничивающие метрики: FPR < 0,15 и p95 задержки < 50 мс. При нарушении вариант B отклоняется.
5. Объём выборки: для обнаружения роста Recall с 0,85 до 0,95 при α = 0,05 и мощности 0,8 нужно около
   140 отказов в каждой группе.
6. Правило решения: v2 заменяет v1, если основная метрика значимо лучше и ограничения не нарушены.

**Ограничения.**
- В тестовой части FD001 всего 100 двигателей, поэтому в проекте A/B-тест выполняется как демонстрация
  методики в теневом режиме; мощности для этапа 2 недостаточно.
- Если по тревоге двигатель отремонтировали, отказ не наступает, и проверить верность тревоги нельзя.
  Поэтому теневой режим идёт первым.
